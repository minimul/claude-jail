# claude-jail

A single-file Bash launcher that runs the [`claude`](https://www.anthropic.com/claude-code) CLI inside a Docker sandbox. The host filesystem stays out of reach (only the launch directory and a small `~/.claude-home` config dir are mounted), the docker daemon is exposed through a filtering shim that limits operations to the compose project rooted at the launch directory, and the jail container is auto-attached to that compose project's networks so claude can reach your services by their compose service names.

## Security model

The jail trades pure isolation for usefulness: it gives claude scoped access to the docker daemon on the host so it can `docker exec`, `docker logs`, `docker compose ps`, etc. against the user's already-running stack — but not against any other container.

There are two layers:

1. **The docker shim** (`/usr/local/bin/docker` inside the image). The real docker CLI is moved to `/usr/local/libexec/docker-real` and replaced with a bash wrapper that:
   - hard-blocks every host-wide command (`run`, `create`, `build`, `pull`, `push`, `image`, `volume`, `network`, `system`, `swarm`, `service`, `stack`, `secret`, `config`, `plugin`, `context`, `login`, `logout`, ...)
   - force-scopes `docker ps` and bare `docker stats` to the project label `com.docker.compose.project.working_dir = $(pwd)`
   - on `docker exec/logs/inspect/cp/start/stop/rm/...`, looks up every container reference in the args and refuses if any of them is not in the project allowlist
   - allows `docker compose <subcommand>` only when no `-f`, `-p`, `--project-directory`, or `--env-file` flag is present (those would let compose pivot to a different project)

2. **The CLAUDE.md scope rule**, generated by the launcher and passed to claude via `--append-system-prompt`. It enumerates the live container names from the compose project and tells the agent which docker commands are allowed and which are blocked. This is the agent-facing half of the same rule the shim enforces mechanically.

> ⚠️ **The shim is a soft fence, not a sandbox primitive.** The host docker socket is bind-mounted into the jail. Anything inside the jail that can talk to `/var/run/docker.sock` directly — `curl --unix-socket`, a statically linked docker binary smuggled in via an MCP server, etc. — bypasses the shim entirely. Treat it as a guard rail for an obedient agent, not a defense against an adversary. If you need a hard isolation boundary, do not mount the host docker socket.

| Attack vector | Protected? | How |
|---|---|---|
| `docker run -v /:/host` to escape into the host filesystem | ⚠️ shim-only | `run` is hard-blocked by the shim. Bypassable via direct socket calls. |
| `docker exec` into an unrelated host container | ⚠️ shim-only | Container ref is checked against the compose project allowlist. Bypassable via direct socket calls. |
| `docker inspect` other host containers (read secrets, env) | ⚠️ shim-only | Same — checked against the allowlist. Bypassable via direct socket calls. |
| `docker network ls`, `docker volume ls`, `docker system info` | ⚠️ shim-only | Hard-blocked by the shim. Bypassable via direct socket calls. |
| Reach host containers on the same compose project network | ⚠️ | Intentional — that is the entire point. |
| Reach unrelated host containers on other networks | ✅ | Only networks belonging to compose containers in `$(pwd)` are attached. (This is enforced by docker, not the shim.) |
| Read/write the launch directory | ⚠️ | Intentional — claude has to be able to edit your code. |
| Tamper with claude credentials | ⚠️ | `~/.claude-home/.claude` is read-write (claude needs to write sessions); `chmod 600 ~/.claude-home/.claude/auth.json`. |

The jail container also runs with `--cap-drop=ALL`, `--security-opt=no-new-privileges`, and as the host's `uid:gid` (not root, with the host docker group GID added so it can talk to the socket). This is why `claude --dangerously-skip-permissions` is permitted — claude refuses that flag when running as root.

## How it works

On first run, `claude-jail` builds a Docker image from an embedded Dockerfile (Node.js LTS on Debian Bookworm with `claude`, the official `docker-ce-cli` + `docker-compose-plugin`, and a small set of CLI tools pre-installed). The real docker binary is moved to `/usr/local/libexec/docker-real`, and the shim takes its place at `/usr/local/bin/docker`. If you edit the script — for example to add apt packages via `CUSTOM_APT_PACKAGES`, or to tweak the shim — the image is automatically rebuilt via `md5sum` change detection.

When you launch the script from a directory:

1. It queries the host docker daemon for any running containers labeled `com.docker.compose.project.working_dir=$(pwd)`. This is the standard label `docker compose` writes on every container it creates.
2. For each match, it lists the docker networks that container is on and dedupes the result. Any `--network NAME` overrides are appended.
3. It also captures the names of those containers and bakes them into a CLAUDE.md-style scope description, which is passed to claude via `--append-system-prompt`.
4. It `docker create`s the jail container with the host docker socket mounted, the host's docker group GID added via `--group-add`, the first compose network attached, and `CLAUDE_JAIL_COMPOSE_WORKDIR=$(pwd)` set in the environment so the in-container shim knows what the project scope is.
5. It runs `docker network connect` for any additional networks, then `docker start -ai`s the container. With `docker create --rm`, the container auto-removes when it exits.
6. If no compose project is currently running for `$(pwd)`, the script prints a warning, starts the jail on only the default bridge network, and the scope prompt tells claude that there are currently no allowed containers.

## Prerequisites

- Docker installed and running on the host.
- The host user must be in the `docker` group (or otherwise able to read/write `/var/run/docker.sock`). The launcher passes that GID into the container via `--group-add`.
- Optional but typical: a `docker compose up -d` already started in your project directory *before* you launch claude-jail, so the script can detect its containers and networks.

## Installation

Copy the script to somewhere on your `$PATH` and make it executable:

```bash
cp claude-jail ~/.local/bin/claude-jail
chmod +x ~/.local/bin/claude-jail
```

## Usage

```
claude-jail [OPTIONS] [-- ARGS...]

Options:
  -e, --env KEY=VAL     Pass an environment variable to the container (repeatable)
  -n, --network NAME    Attach the jail container to an extra docker network (repeatable)
  -r, --rebuild         Force rebuild of the Docker image
      --no-cache        Rebuild without using Docker cache
  -s, --shell           Start a bash shell instead of claude
  -R, --resume UID      Resume a previous session by its ID
  -c, --continue        Continue the most recent session
      --safe            Do NOT pass --dangerously-skip-permissions to claude
  -h, --help            Show this help message
```

Arguments after `--` are passed through to claude.

By default, claude-jail launches claude with `--dangerously-skip-permissions`. The jail's docker access is already filtered by the shim and only the launch directory is writable on the host, so the per-tool permission prompts add friction without meaningful protection. Pass `--safe` to restore them.

### Examples

```bash
# Typical workflow: bring your stack up first, then claude
docker compose up -d
claude-jail

# Pass arguments directly to claude
claude-jail -- -p "Summarize this codebase"

# Pass environment variables into the container
claude-jail -e ANTHROPIC_API_KEY=sk-ant-... -e MY_VAR=hello

# Attach to additional non-compose networks
claude-jail --network my-shared-net --network another-net

# Open a shell inside the jail instead of running claude
claude-jail --shell

# Force a full image rebuild
claude-jail --rebuild
```

If `--shell` is used while a jail container from the same launch directory is already running, the script `docker exec`s into it instead of starting a new one. Note that an already-running jail keeps the networks it was created with: bring up new compose services *before* launching claude-jail if you want them auto-attached. New compose containers added to the *same* project after launch are still pickable up by the shim's allowlist (which is computed live), but they will not be reachable by service-name DNS unless you re-launch.

## Operational safety

The jail filters the host docker daemon, but does not isolate it. Keep these rules in mind:

1. **Never launch `claude-jail` from `$HOME`, `/`, or any directory containing unrelated projects.** The launch directory is mounted read-write and claude runs with `--dangerously-skip-permissions` by default, so anything under `$(pwd)` can be modified or deleted without confirmation. Launch from a specific project directory you are willing to let claude rewrite.
2. **Do not treat the docker shim as an isolation boundary.** It is a guardrail. The host docker socket is mounted into the jail; an attacker (or a misbehaving MCP server) inside the jail that talks directly to `/var/run/docker.sock` can do anything the docker daemon can do. If you need hard isolation, run claude in an environment that does not have the socket mounted.
3. **Protect your API key.** `~/.claude-home/.claude/auth.json` is mounted read-write into the container; a compromised session can read it. At minimum:
   ```bash
   chmod 600 ~/.claude-home/.claude/auth.json
   ```
   Prefer short-lived OAuth credentials over a long-lived `ANTHROPIC_API_KEY` when possible.
4. **Egress is not restricted.** The jail container can reach the public internet. If you need tighter control, attach it to a network with an explicit egress policy via `--network`.
5. **Compose-network reachability is symmetric.** The jail is on the same docker network as your compose services, so any process inside any of those services can also reach the jail container by IP. Do not put untrusted services on the same compose network.

## Configuration

### API keys

Claude state is persisted on the host under `~/.claude-home` and mounted into the container as `/home/node/.claude` (plus `~/.claude-home/.claude.json` → `/home/node/.claude.json`). `HOME` inside the container is `/home/node`, so credentials written there are available on every run without setting environment variables.

For example, to configure your Anthropic API key:

```bash
mkdir -p ~/.claude-home/.claude
echo '{"anthropic":{"type":"api_key","key":"sk-ant-..."}}' > ~/.claude-home/.claude/auth.json
chmod 600 ~/.claude-home/.claude/auth.json
```

### Adding packages

To install extra packages into the image, edit the `CUSTOM_APT_PACKAGES` variable near the top of the script:

```bash
CUSTOM_APT_PACKAGES="jq git tmux sqlite3"
```

Save the file and the image will rebuild automatically on the next run.

## Volume mounts

| Host | Container | Mode | Purpose |
|---|---|---|---|
| `$(pwd)` | same path | read-write | Current working directory (path-mirrored so paths in your tooling resolve identically inside and outside the jail) |
| `/var/run/docker.sock` | `/var/run/docker.sock` | read-write | Host docker socket; reached only via the filtering shim at `/usr/local/bin/docker` |
| `~/.claude-home/.claude` | `/home/node/.claude` | read-write | claude configuration, sessions, auth |
| `~/.claude-home/.claude.json` | `/home/node/.claude.json` | read-write | claude user settings file |

## Included tools

The image contains:

- `claude` (installed via `npm install -g @anthropic-ai/claude-code`)
- `docker-ce-cli` and `docker-compose-plugin` (the real binary lives at `/usr/local/libexec/docker-real`; the shim at `/usr/local/bin/docker` is what `$PATH` resolves to)
- `curl`, `ca-certificates`, `gnupg`, `build-essential`
- `jq` (via the default `CUSTOM_APT_PACKAGES`)

Add anything else you need via `CUSTOM_APT_PACKAGES`.

## Docker shim reference

Inside the jail, `docker` is the shim. Its behavior:

| Subcommand | Behavior |
|---|---|
| `version`, `info`, `help` | Pass through to the real docker. |
| `ps` | Always force-injected with `--filter label=com.docker.compose.project.working_dir=$WORKDIR`. |
| `stats` (no positional args) | Auto-targets every container in the project. |
| `stats <ctr>...` | Validated against the project allowlist. |
| `exec`, `logs`, `inspect`, `top`, `port`, `diff`, `cp`, `wait`, `attach`, `kill`, `stop`, `start`, `restart`, `pause`, `unpause`, `rename`, `update`, `rm` | Validated against the project allowlist. Any container reference (including `container:/path` for `cp`) outside the project is rejected. |
| `compose <subcommand>` | Allowed, but `-f`, `--file`, `-p`, `--project-name`, `--project-directory`, and `--env-file` are rejected because they would let compose pivot to a different project. |
| `run`, `create`, `build`, `buildx`, `builder`, `pull`, `push`, `tag`, `save`, `load`, `import`, `export`, `history`, `commit`, `image`, `images`, `rmi` | **Hard-blocked.** |
| `network`, `volume`, `system`, `swarm`, `node`, `service`, `stack`, `secret`, `config`, `plugin`, `context`, `login`, `logout`, `trust`, `search` | **Hard-blocked.** |
| Anything else | **Hard-blocked** with an "unrecognized" message. |

When the shim refuses a command, it prints both the reason and the active scope to stderr, e.g.:

```
claude-jail docker shim: refusing container 'bldup-3001-rails-1' is out of scope
claude-jail docker shim: scope = compose project working_dir=/home/me/projects/myapp
```

The shim resolves the project scope from the `CLAUDE_JAIL_COMPOSE_WORKDIR` environment variable that the launcher sets at create time. If you want to test the shim in isolation you can override it.

## Testing the shim and compose-network access

A `docker-compose.yml` is included to verify both the network attach and the docker shim. The relevant service is `test-web`, an alpine container that listens on port 8080 and replies with `OK`.

```bash
# 1. From the claude-jail directory, bring the test service up on the HOST
docker compose up -d test-web

# 2. Launch a jail shell from the same directory
claude-jail --shell
```

You should see something like

```
Attaching jail to networks: claude-jail_default
Compose containers in scope: claude-test-web
```

before the shell appears. Inside the jail:

```bash
# 3. Hit the service by its compose service name (network attach)
curl http://test-web:8080
# => OK

# 4. The shim only sees in-scope containers
docker ps --format '{{.Names}}'
# => claude-test-web

# 5. Allowed: exec into an in-scope container
docker exec claude-test-web echo hi
# => hi

# 6. Blocked: exec into anything else
docker exec some-other-host-container echo hi
# => claude-jail docker shim: refusing container 'some-other-host-container' is out of scope

# 7. Blocked: any host-wide command
docker run --rm alpine echo hi
# => claude-jail docker shim: refusing 'docker run' is host-wide and not allowed from inside claude-jail

docker network ls
# => claude-jail docker shim: refusing 'docker network' is host-wide and not allowed from inside claude-jail

# 8. Compose still works for the local project
docker compose ps
# => NAME              STATUS
# => claude-test-web   Up 30 seconds
```

Tear down when you are done:

```bash
exit                       # leave the jail
docker compose down        # stop test-web on the host
```

### Verifying the shim is in the right place

From inside the jail:

```bash
# The shim is what $PATH resolves to
which docker
# => /usr/local/bin/docker

file $(which docker)
# => /usr/local/bin/docker: Bourne-Again shell script ...

# The real docker is hidden one directory over
ls -l /usr/local/libexec/docker-real

# Running as your host user, not root, with the host docker group added
id
# => uid=1000(...) gid=1000(...) groups=1000(...),NNN
```
